# Reproduction notes, 2026-10-06 (kwerft-dedi-1)

Two problems seen in production on the agent cluster kwerft-dedi-1 (single
node, 65.108.43.91, Cilium, v0.6.0-rc.x), both fixed after v0.6.0-rc.7.

## 1. `egress: https` cannot reach the cluster's own hostnames

**Symptom.** A Task (or App) with `egress: https` (the default) times out on
the hostnames this same cluster serves: from an egress-https Task on
kwerft-dedi-1, https://router.hatchure.app/healthz and
https://router-next.apps.kwerft.dev/healthz time out, while
cloud.kwerft.dev and example.org answer 200.
hatchure's gh-activate Task checked its new route at
https://router.hatchure.app, timed out 60 times and rolled back a good release.

**Cause.** `egress: https` was rendered as "TCP 443 to `0.0.0.0/0` minus
RFC 1918 and 169.254/16": a `toCIDRSet` in the App's CiliumNetworkPolicy, an
`ipBlock` in the Task's Kubernetes NetworkPolicy. The cluster's own hostnames
resolve to a node's public address, where Traefik listens on the host network
(hostNetwork DaemonSet, ports 80/443). Cilium gives every node address the
reserved identity `host` (this node) or `remote-node` (another node), and CIDR
selectors never match those identities. Cilium's docs (Layer 3, CIDR based)
say CIDR rules do not apply to traffic where both sides are managed by
Cilium or use a node's IP; such traffic has to be allowed with entities.
So the connection to the node's own IP (the hairpin) was dropped as
`Policy denied`, and curl hung until its timeout. `egress: all` was never
affected: it renders no egress section, so nothing outbound is denied.

**Fix.** `egress: https` also allows TCP 443 to the entities `host` and
`remote-node` (`appEgress` in `internal/controllers/traffic_render.go`), only
443: SSH, the Kubernetes API (6443), the kubelet and metrics ports on the
nodes stay closed. Tasks now get a CiliumNetworkPolicy (`<task>.task`, default
deny ingress, the same egress as an App) instead of a Kubernetes
NetworkPolicy, which cannot name entities. `egress: none` is unchanged
(DNS and pods in the cluster only). Tests:
`TestEgressReachesTheClustersOwnIngress`, `TestTaskRendersJob`,
`TestTaskFromAppInheritsAndOverrides` (the old NetworkPolicy is removed).

**Reproduce** (on a test cluster, never prod). Replace the project and the
hostname with an App this cluster serves (the console's own hostname works
too):

```yaml
# kubectl apply -f - ; then kubectl -n demo logs job/hairpin
apiVersion: kwerft.dev/v1alpha1
kind: Task
metadata: {name: hairpin, namespace: demo}
spec:
  source: {image: {ref: curlimages/curl:8.16.0}}
  egress: https
  command: [sh, -c, 'for u in https://example.org https://APP.apps.example.com; do curl -s -o /dev/null -m 10 -w "%{http_code} $u\n" "$u"; done']
```

Before the fix: `200 https://example.org`, then `000 https://APP…` after
10 s. After it: two 200s (or the app's own status). Cilium's monitor shows
the drop, to the node's address, which has the identity `reserved:host`:

```
kubectl -n kube-system exec ds/cilium -c cilium-agent -- cilium-dbg monitor --type drop
kubectl -n kube-system exec ds/cilium -c cilium-agent -- cilium-dbg ip get <node public IP>   # identity 1 = reserved:host
```

The same Task with `egress: none` must still print `000` for both.

## 2. An OOM-killed Task shows only exit code 137

**Symptom.** A Task whose container ran out of memory showed
`exitCode: 137` and nothing else in `kubectl get tasks.kwerft.dev -o yaml`
and in the console's Jobs view; 137 (SIGKILL) reads like a crash.
hatchure's rclone sync with 8 transfers hit the default size (small:
256 MiB, request = limit).

**Fix.** The Task status keeps the container's `terminationReason`
(`OOMKilled`, `Error`, `Completed`) and, for an OOM kill, `memoryLimit`.
The Ready condition becomes `OutOfMemory`: "The run used more memory than
its limit (256Mi) and was stopped; give the Task a larger size (exit code
137)". `kubectl get tasks` shows a Reason column; the console says "out of
memory (limit 256Mi)" in the runs table, the failed-schedule banner, the
alerts and the map. Tests: `TestTaskOutOfMemory`,
`TestTaskSummaryOutOfMemory`, `web/src/jobs.test.ts`.

**Reproduce:**

```yaml
apiVersion: kwerft.dev/v1alpha1
kind: Task
metadata: {name: hog, namespace: demo}
spec:
  source: {image: {ref: alpine:3.22}}
  size: small
  command: [sh, -c, 'head -c 400m /dev/zero | tail']   # tail holds the one 400 MB "line"
```

`kubectl -n demo get task hog` → `Failed  137  OOMKilled`; the Task's
Ready message names the 256Mi limit. With `size: large` (2 GiB) it
succeeds.

**Default size.** Kept at small. A larger default would only move the
threshold (rclone's memory grows with `--transfers` and `--buffer-size`)
and reserve more memory for every Schedule without a size; the message now
says what to change. hatchure's rclone Task should set `size: medium` or
`large` (or lower `--transfers` / `--buffer-size`).
