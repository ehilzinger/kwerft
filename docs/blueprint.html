Kwerftself-hosted Kubernetes console for Hetzner
blueprint · draft 2 · 4 Oct 2026

Rent a Hetzner box, run one script, manage containers from the browser.

Kwerft installs a hardened single-node Kubernetes (k3s) on a fresh Ubuntu server and puts a console on top of it: deploy container images, watch them, and administer network rules, domains, nodes, clusters and access — without hiding Kubernetes from the people who want it.

  • Installcurl … | bash -s -- --domain ops.acme.dev, idempotent, non-interactive with flags
  • Runtimek3s · Cilium · Traefik · cert-manager · VictoriaMetrics/Logs
  • SourcesImages from any registry, or Git repositories built in-cluster on push
  • ConsoleGo API + controllers, React UI, one binary in one Helm chart
  • HostsHetzner Cloud and dedicated servers · Ubuntu 22.04–26.04 LTS · 8 GB RAM recommended (the platform uses about 2.5 GB) · 4 GB with --lite

Goals & principles

A Hetzner-aware control panel that makes Kubernetes feel like one server

The product has one job: take a freshly rented Hetzner machine to “my containers are running behind HTTPS and I can see what they're doing” in under ten minutes, then grow to multiple nodes and clusters without a re-platform. Five principles shape every decision below.

One command, zero follow-upThe installer is idempotent and fully flag-driven, and remembers its flags. Running it again repairs the install; a newer release's installer upgrades Kwerft and its platform, while Kubernetes is upgraded from the console. Cloud-init can call it unattended.
Kubernetes is the databaseEvery app, rule and domain is a custom resource. The UI writes those resources; controllers turn them into native objects. GitOps works for free.
Fits an 8 GB boxThe platform uses about 2.5 GB of RAM (measured), leaving most of an 8 GB server for real workloads. 4 GB works with --lite.
Secure by defaultProjects are isolated, the Kubernetes API is private, secrets are encrypted, every shell session and change is audited.
Never a dead endPower users get YAML export, a scoped kubeconfig and kubectl. Kwerft-managed objects are labelled, so hand-made resources live alongside without conflict.

Build vs. adopt

Check these before committing: Rancher manages many clusters but is heavy and not Hetzner-aware; Portainer has a friendly UI with thinner network administration; Coolify and Dokploy are Docker/Swarm-based PaaS rather than Kubernetes; hetzner-k3s provisions clusters from a CLI with no console. Kwerft's niche is the combination: Hetzner-native provisioning and firewalls, Kubernetes underneath, a one-script install and an opinionated UI on top.

How a change flows

  1. The UI sends PUT /api/v1/projects/storefront/apps/api. The API checks the user's role, then writes the App custom resource while impersonating that user, so Kubernetes RBAC is the final gate.
  2. The App reconciler renders a Deployment, Service, HTTPRoute, CiliumNetworkPolicy and PVCs, applies them with server-side apply, and writes progress into App.status.
  3. The UI is subscribed over WebSocket to a shared informer cache; rollout progress, pod events and log lines stream back without polling.

The install script

One idempotent bash script, safe to re-run, safe to automate

The script is the product's front door, so it gets the same care as the UI: set -Eeuo pipefail, shellcheck-clean, every step logged to /var/log/kwerft/install.log, and every download pinned by version and SHA-256.

Stages

Each stage records completion in /var/lib/kwerft/stages, and a failed run resumes where it stopped. Every stage but Kubernetes converges on each run (packages, firewall, Helm, the platform charts, Kwerft), so re-running a newer release's installer upgrades Kwerft and its platform with the flags remembered in /var/lib/kwerft/install.env. k3s keeps the version it was installed with, on every node, until the console upgrades it (Settings › Updates, through system-upgrade-controller, node by node); a re-run says when it is older than the release's pin.

  1. Preflight — detects Hetzner Cloud vs. dedicated, root, Ubuntu 22.04/24.04/26.04, x86_64 or arm64, ≥ 4 GB RAM, ≥ 30 GB disk, ports 80/443 free, outbound HTTPS, clock sync. Fails with a specific message and exit code.
  2. System prep — apt packages, kernel modules and sysctls for Cilium, swap off, chrony, unattended-upgrades, optional SSH hardening (--harden-ssh).
  3. Firewall baseline — nftables allowing 22/80/443 publicly and cluster ports only on the private interface. Cilium host policies take over once running.
  4. Kubernetes — k3s server with flannel, kube-proxy and the bundled policy controller disabled, secrets encryption on, API bound to the private IP.
  5. Platform — Helm installs Cilium, cert-manager, Traefik config, the observability stack and CRDs from one release manifest.
  6. Kwerft — Helm installs the console, waits for readiness, requests the console certificate.
  7. Handoff — verifies DNS and TLS end to end, writes a single-use setup token (24 h) to a 0600 file, prints the URL and a summary.

Exit codes are stable for automation: 0 success, 10 preflight, 20 network/DNS, 30 Kubernetes, 40 platform, 50 Kwerft.

Security model

Assume the server is on the open internet, because it is

  • Bootstrap: the console is unusable until someone presents the setup token from the server's disk. No default passwords anywhere.
  • Authorization: Kwerft roles map to Kubernetes ClusterRoles bound per project namespace. The API impersonates the signed-in user, so a bug in Kwerft's own checks cannot exceed that user's Kubernetes rights.
  • Kubernetes API: bound to the private network only; external kubectl goes through Kwerft's authenticating proxy with short-lived, scoped kubeconfigs.
  • Secrets: k3s secrets encryption at rest; secret sets are project-scoped and write-only for developers; owners and admins reveal a value after their password, audited; values never appear in audit entries, logs, YAML exports or pushes between instances.
  • Shell access: exec sessions are role-gated, time-limited and recorded (asciinema format) for review.
  • Network: default-deny between projects, WireGuard between nodes, host firewall managed as code, Hetzner Cloud Firewall mirrored for cloud nodes.
  • API tokens: scoped to projects and verbs, always expiring, shown once, stored hashed.
  • Supply chain: signed Kwerft images (cosign), pinned component digests, SBOMs published per release; the installer verifies checksums before executing anything it downloads.
  • Session hygiene: HTTPS only with HSTS, SameSite cookies, CSRF tokens, rate-limited sign-in, passkeys preferred.

Nodes & clusters

Grow in three steps without reinstalling

  1. Add workers to the first cluster. Cloud servers are created through the Cloud API with cloud-init that runs the join script; dedicated (Robot) servers run the join command shown in the UI. Nodes talk over a Cloud Network or vSwitch where available and WireGuard otherwise.
  2. Make it highly available. Promote to three control-plane nodes (embedded etcd). Put a Hetzner Load Balancer in front of the ingress, or a Floating IP for dedicated-only setups, and move platform state to replicated storage.
  3. Add more clusters. Kwerft provisions a new k3s cluster on Hetzner Cloud (or adopts any existing one) and installs kwerft-agent. Apps, rules and alerts are scoped by cluster in the UI.

Mixed dedicated + cloud clusters are supported but need care: Hetzner's vSwitch-to-Cloud-Network coupling is per location, so cross-location nodes fall back to WireGuard over public IPs.

Risks & decisions

What could go wrong, and what we decided

  • Single node is a single point of failure. Make it explicit in the UI and push automatic etcd snapshots to Object Storage from day one.
  • Resource overhead on small servers. Hold the measured ~2.4 GB in CI; offer a “lite” profile (no Hubble, shorter retention) for 4 GB machines.
  • Dedicated vs. Cloud asymmetry. The Robot API cannot create servers on demand like the Cloud API; dedicated nodes always join by script, and vSwitch coupling to Cloud Networks only works within one network zone.
  • Firewall lock-out. Mitigated by caller-IP checks and an automatic revert timer, plus an install.sh --reset-firewall rescue path via the Hetzner console.
  • Upstream churn. k3s, Cilium and Gateway API move quickly; pin versions in a release manifest and test upgrades from N-1 and N-2.
  • Apple container is young. Its Kubernetes plugin is experimental and cannot survive a restart, container machine run loses argument quoting, and the XPC API is not a public contract. The Mac app pins a supported version, talks only to the CLI's JSON output and keeps desired state outside the local cluster.
  • Owning a kernel. Kwerft for Mac ships its own kernel. Building it takes three minutes; tracking Apple's config and kernel security releases is a standing cost, reduced by upstreaming the missing options to Apple.
  • Backups carry secret values. k3s encrypts Secrets only inside etcd; Velero writes them to Object Storage as they are. Backups are encrypted before secret sets ship.
  • Builds and jobs compete with apps for memory. Builds run as Jobs with limits and queue one at a time on small nodes; Tasks run in a lower priority class, so a job goes before a service; heavy users add a build node pool.
